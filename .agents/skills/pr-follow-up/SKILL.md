# PR 跟进

创建 PR 或向其推送后，安排一个子代理跟进，提供 PR 链接、分支、提交 SHA 和按
[CI 规则](../../../docs/ci.md)预期触发的检查。主代理继续开发。同一个 PR 只需一个跟进代理，
推送新提交后更新跟进目标。

## 跟进频率和交接

- 每个 PR 只保留一个跟进子代理。新推送到达后，将现有子代理切换到新 SHA，停止跟进旧提交。主代理继续开发，已有子代理时不再启动重复的状态轮询。
- 等待 runner 时每 2–5 分钟查一次，任务运行后每 1–2 分钟查一次。使用可被新提交或用户消息打断的等待。
- 仅在状态有实质变化时通知主代理，例如任务开始运行、发现失败、出现有效审查意见、遇到阻塞或所有检查通过。消息附上当前 SHA 和相关链接，无变化时不重复汇报。
- 主代理收到全绿通知后核对远端最新 SHA、预期检查和未解决讨论。已有合入授权时，使用核验过的 SHA 合入。默认使用 GitHub 的 **Create a merge commit**，确认合入成功后删除 PR 的远端源分支。

## PR 标题和描述

PR 标题和描述默认使用英文。

创建 PR 或变更范围发生变化时，对照整个 PR 相对基线的差异，核对标题和描述。标题概括主要改动，描述说明最终行为、相关验证和仍待验证的事项。范围变化后重写过时的标题和描述，区分本地已通过的验证和仍在运行的 CI。

## CI 和审查讨论

1. 确认 PR 最新提交，跟踪对应的 CI 和审查讨论。检查未出现时先核对路径规则，若应触发则排查原因。
2. 查看失败日志。确认是临时 runner 故障时，在同一提交上重试。可复现的问题与主代理协调修复，并在本地验证。
3. 对照当前差异检查未解决的讨论。修复有效问题，等修复出现在 PR 后标记为 Resolved。已有修复或经核实不再适用的讨论也应关闭。仍有分歧或未解决的问题保留并报告。
4. 主代理管理活动工作树、提交和推送。子代理可在明确分工后独立准备修复。推送后重新核对新提交，交付或获准合入前报告提交 SHA、检查结果、已关闭讨论和阻塞项。

子代理不可用时由主代理跟进。提交、推送和合入沿用任务已有的授权范围。
