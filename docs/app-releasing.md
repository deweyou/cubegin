# App 发布规范

使用 [release](../.agents/skills/release/SKILL.md) 筹备首发或新版本线，使用 [patch](../.agents/skills/patch/SKILL.md) 修补已上架的版本。各 App 独立管理公开版本与构建号。当前执行入口是 [iOS 发包手册](../apps/ios/docs/releasing.md)。Rust 和平台 SDK 使用 [SDK 发布流程](releasing.md)。

## 锁定范围与候选

| 阶段 | 约定 |
| --- | --- |
| 发布评审 | `release` 先展示相对上一正式版本的差异、中英文用户说明和具体版本选项，再等确认。`patch` 先确认问题和线上基线，修复后确认差异与说明，再出包。 |
| 分支与草稿 PR | 从确认的提交切 `release/<app>/X.Y`，或从实际线上 tag 切 `patch/<app>/X.Y.Z`。相对 `main` 有可比较的提交后，推送临时候选分支并创建指向 `main` 的 Draft PR。 |
| 准备 | 变更说明按 App 维护。商店草稿、应用标识、版本号和已有 build 在出包前核对。复用仓库的商店资料，核对受影响字段和截图。商店资料准备可与出包并行。 |
| 构建与验收 | 出包时分配 build。从已推送、已预留构建号的确切 SHA 构建，保持构建工作区干净。登记 App、公开版本、build、SHA、产物校验和与归档位置。归档核验后上传商店，随后按平台流程验收。确认上线后记录实际发布日期和渠道状态。 |
| 返工 | 改代码后仍在原分支，公开版本保持不变，重新出包递增 build。只更换商店资料时复用原有候选。 |
| 上架与回合 | 等商店审核通过并确认上线。根据实际发布的 build 查候选记录，从该 SHA 打 `<app>/vX.Y.Z`，核对草稿 PR 后转为待审核并合入。保留主线的新版本信息和下一版条目，带回本版的修复、测试、发布说明和商店资料。 |

构建号按 App 身份分配。同一 App 的发布与补丁候选共用编号序列，渠道各自记录实际分发的 build。若未来某 App 的同一公开版本在多个渠道使用不同 SHA，各渠道用 `<app>/<channel>/vX.Y.Z` 定位线上基线。单一渠道时用 `<app>/vX.Y.Z`。

Draft PR 记录公开版本和候选 SHA，预留后补上 build 编号，返工后更新。送测、提审、审核中和审核通过待发布期间保持草稿状态。PR 检查按 [PR 合入规则](ci.md) 执行，草稿 PR 可在后台跑检查。候选归档和上传无需额外调度或等待 CI。

## 持续推进与交接

先确定用户本轮要到达的节点。每次推进都读取远端分支、候选记录和商店状态，再执行当前获准的下一步并回读验证。持续推进到本轮目标。等待上传处理或审核时，先完成能独立做的事，按用户要求继续观察状态变化。

- 交接记录保留版本、build 和候选 SHA，最后核验的后台状态，以及下一步和所需授权。进度更新集中在阶段变化、具体卡点和需要用户动作时。
- 遇到中断先检查操作是否已经生效。已经登记的原包通过校验后直接复用。包已生成但登记失败时补登记，确需重建时分配新 build。恢复会话时先回读最后记录的节点，再决定是否重试。
- 需要用户登录、真机验收、确认声明或执行其保留的操作时，打开对应页面（如可用），说明卡点、具体按钮或字段、完成后要核对的状态。其余获准的工作继续推进。收到回复后验证实际结果，接着执行下一步。
- 可重试的处理由当前发布会话跟进。后续完全依赖外部状态时，交代当前等待的结果和重启位置。达到用户指定节点后，报告该节点已核验的结果。
- 商店已审核但仍待发布时，保留候选分支。正式上线且关联 build 对得上，才打正式 tag。已有同名 tag 指向同一 SHA 时复用；指向其他 SHA 时停下来核对。

回合默认沿用草稿 PR，以 merge 方式保留发布提交历史。转为待审核前，核对该 PR 包含实际上线的 SHA，以及同一版本适用的商店资料和发布文档。若草稿分支还包含待后续发版的 App 改动，从正式 tag 创建收尾分支，带回本版适用的资料提交，并在 PR 中关联原草稿。按最新提交核对合入检查和审查意见。合入后确认远端 tag 正确，使用 `git merge-base --is-ancestor <tag> origin/main` 验证发布提交已进入主线。确认临时分支的额外提交已妥善保留，再清理临时分支。正式 tag 和远端候选记录长期保留。
