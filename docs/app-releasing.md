# App 发布规范

使用 [release](../.agents/skills/release/SKILL.md) 筹备首发或新版本线，使用 [patch](../.agents/skills/patch/SKILL.md) 修补已上架的版本。各 App 独立管理公开版本与构建号。当前执行入口是 [iOS 发包手册](../apps/ios/docs/releasing.md)。Rust 和平台 SDK 使用 [SDK 发布流程](releasing.md)。

## 锁定范围与候选

| 阶段 | 约定 |
| --- | --- |
| 发布评审 | `release` 先展示相对上一正式版本的差异、中英文用户说明和具体版本选项，再等确认。`patch` 先确认问题和线上基线，修复后确认差异与说明，再出包。 |
| 分支 | 从确认的提交切 `release/<app>/X.Y`，或从实际线上 tag 切 `patch/<app>/X.Y.Z`。维护者可直接推送临时候选分支，正常开发和发布回合走 PR。 |
| 准备 | 变更说明按 App 维护。商店草稿、应用标识、版本号和已有 build 在出包前核对。文案、截图和审核资料可与候选 CI 并行准备。 |
| 构建与验收 | 出包时分配 build。只从已推送、工作区干净且所需 CI 通过的确切 SHA 构建。登记 App、公开版本、build、SHA、产物校验和与归档位置。确认上线后记录实际发布日期和渠道状态。 |
| 返工 | 改代码后仍在原分支，公开版本保持不变，重新出包递增 build。只更换商店资料时复用原有候选。 |
| 上架与回合 | 根据商店实际发布的 build 查候选记录，从该 SHA 打 `<app>/vX.Y.Z`，再开回合 PR。保留主线的新版本信息和下一版条目，带回本版的修复、测试、发布说明和商店资料。 |

构建号按 App 身份分配。同一 App 的发布与补丁候选共用编号序列，渠道各自记录实际分发的 build。若未来某 App 的同一公开版本在多个渠道使用不同 SHA，各渠道用 `<app>/<channel>/vX.Y.Z` 定位线上基线。单一渠道时用 `<app>/vX.Y.Z`。

## 持续推进与交接

每轮先读远端分支、候选记录和商店状态，再执行当前获准的下一步，并回读验证。等 CI、上传处理或审核时，先完成可以并行的事项。继续旧任务时从现有记录恢复。

- 分清已预留、已归档、商店已收包、测试已验收、已加入审核草稿、已送审和已上线。商店后台的实际状态决定下一步。
- 遇到中断先检查操作是否已经生效。已经登记的原包通过校验后直接复用。包已生成但登记失败时补登记，确需重建时分配新 build。
- 需要用户登录、验证身份、确认声明或执行其保留的操作时，一次说明当前卡点、页面链接、要点的按钮或要填的内容，以及确认后将回读的状态。可并行的工作继续推进。仅在到达用户要求的阶段，或后续确实依赖用户或外部状态时交接。
- 商店已审核但仍待发布时，保留候选分支。正式上线且关联 build 对得上，才打正式 tag。已有同名 tag 指向同一 SHA 时复用；指向其他 SHA 时停下来核对。

回合默认用 merge PR。候选分支 tip 领先于已上架的 SHA 时，从正式 tag 创建收尾分支。PR 合入后确认远端 tag 正确，使用 `git merge-base --is-ancestor <tag> origin/main` 验证发布提交已进入主线。确认临时分支的额外提交已妥善保留，再清理临时分支。正式 tag 和远端候选记录长期保留。
